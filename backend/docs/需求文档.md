# bald-admin 需求文档

> 目标：作为 `bald` 框架的参考实现，验证框架能力在真实管理后台业务下的可用性。
> 本文件是范围与验收基线；具体技术选型见同目录 `设计文档.md`。

## 1. 背景与目标

- **形态**：前后端 monorepo。`backend/` 是独立 Go module，提供 HTTP(gin)、gRPC 与
  grpc-gateway 转码三种入口；`frontend/` 是 Vue 3 管理前端，消费同一份 proto 契约。
- **重构目的**：验证 bald 框架（核心零耦合 + 桥接子模块）能否承载后台管理系统的
  横切与业务需求，重点在认证/授权、多租户、审计与可观测性。
- **约束**：所有横切能力必须经 bald 契约实现或 contrib 桥接，业务不直连引擎；
  外部依赖禁止 fake/mock/stub（见设计文档 §0）。

## 2. 功能需求

### 2.1 业务域

| 域 | 落地说明 |
|----|----------|
| auth | 登录/登出/刷新令牌/验证码/多因素，走 `bald-authn-jwt` |
| user / identity / org | 用户、组织单元、岗位，业务 CRUD |
| tenant | 租户管理（平台侧），多租户隔离的租户维度来源 |
| permission / menu / permgroup | 角色/权限点/菜单/权限组，RBAC 授权走 `authz.Authorizer` |
| dict / language | 数据字典（Cache-Aside）、语言表 |
| file | 文件上传/下载，`bald/oss/minio` 桥接 |
| audit / auditlog | 操作/登录/接口审计记录与分页查询 |
| dashboard / portal / plan / task / message / cachemonitor / mfa | 管理面与运维面业务 |
| serviceinfo | 服务自述端点（`/v1/ping`、`/v1/info`） |

### 2.2 横切需求（bald 能力验证点）

- **认证**：Bearer JWT 校验与令牌签发（`bald-authn-jwt`），`AuthClaims` 强类型注入 context。
- **授权**：RBAC 模型基于 `authz.Authorizer`；不把 casbin 引入核心，业务侧桥接。
  REST 与 gRPC 的权限点经传输中立归一化，同一份策略对两种协议生效。
- **多租户**：`store.RegisterTenant("tenant_id", store.DefaultTenantFunc)` 显式开启，
  查询与写入自动带 `tenant_id`。
- **数据权限**：`store.RegisterDataScope` 注入范围条件（仅本人/本部门/全部等）。
- **存储**：统一 `store.Store[T]` 泛型仓储，GORM 桥接，三策略分页（Page/Offset/Token）。
- **配置**：proto-first（`bconf`），viper 四源合并，flag/env/yaml 覆盖次序固定。
- **生命周期**：`appkit.Run` 三阶段优雅停机；`pkg/appkit` 注册表统一管理
  server/provider/middleware。
- **可观测**：日志/错误/链路依赖倒置；Prometheus 本地抓取 + OTLP 远端直推。
- **CLI/代码生成**：复用 `bald codegen`、`gen app`、`gen domain`；插件发现风格与 kubectl 一致。

### 2.3 协议与接口

- 同时暴露 gRPC、HTTP(gin) 与 grpc-gateway 转码；proto 为唯一契约真相源。
- OpenAPI 由 proto 注解生成并经 `//go:embed` 内嵌，前端 TypeScript 由同一份 spec 生成。

### 2.4 部署与运维

- 本地零外部依赖可跑通 e2e（SQLite 内存库 + 可选 Redis/MinIO）。
- 生产形态：PostgreSQL + Redis + MinIO + Nacos + OTLP Collector。
- 配置文件不入库；模板 `configs/bald-admin.yaml.example` 提供全部可配置项。

## 3. 非功能需求

- **零核心耦合**：`bald-admin` 是独立 module，零 `replace` 消费 bald 发布版本；
  不向 bald 核心引入任何业务/引擎依赖。联调本地核心时临时加 `replace`，不提交。
- **可测试**：每个业务域具备单元测试；关键链路具备 e2e（真实 gin + store + 拦截器链）。
- **文档一致**：proto 注解驱动 OpenAPI 与前端类型，生成物禁止手改。

## 4. 验收标准

1. `cd backend && go build ./... && go test ./...` 通过（独立 module）。
2. e2e 覆盖至少一条完整链路：登录 → 带令牌访问受限接口 → 越权 403 → 跨租户 404。
3. 认证、授权、租户隔离均有可演示路径。
4. 不出现 fake/mock/stub 充当外部依赖。
5. 修改 bald 核心后，在本仓库一键验证无回归。

## 5. 范围边界

- **非目标**：功能面不做全量覆盖；前端只作为契约消费者，用于验证
  proto → OpenAPI → TS 的同步链路。
- **允许的简化**：无外部数据库时使用 SQLite 内存库（仍是真实 GORM+DAL 路径），
  须显式标注，不得伪装成已接入外部依赖。
